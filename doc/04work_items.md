# 今後の作業リスト

更新日: 2026-09-22

以下の順序・優先度は提案であり、着手の決定ではない。OR検索・読書状態・MCP／SKILLの保留は継続する。設計上の決定事項はdoc/01、実施した検証結果はdoc/02に記録する。

## 現在できていること

- TypeScript・pnpm・Biomeとコミット前チェックを備えた開発環境。
- Kindleの購入済み一覧取得・保存JSON取り込み、BOOK☆WALKERの先頭25冊の部分取得・取り込み。
- 両ストアの所有情報と書誌情報を分けたSQLite保存、語句AND検索・出版社絞り込み・詳細取得。
- 所有・書誌のストア別アダプター化と、架空の第3ストアによる共通経路の検証。
- 実蔵書DBへの2ストアのデータ取り込みと横断検索。書誌補完は少数のみで、全所有書籍の分類検索を網羅する状態ではない。

## 先に検討する候補

| ID | 作業 | 内容・完了の目安 | 前提・取得範囲 |
|---|---|---|---|
| A1 | 検索目的と不足データの棚卸し | 当初の検索例を「現在できる／書誌不足／機能不足／読書状態待ち」に分ける。種類・出版社・同著者・Blender・3Dモデリング・Python・未読の続巻・全巻未着手を対象に、次に埋める不足を決める | まず保存済みDBで確認。新たな取得は不要 |
| A2 | 書誌補完の対象選択と実行管理 | 未取得・取得失敗・項目欠損を区別し、ストア・商品・件数を指定して少数処理できる案を決める。成功済みを繰り返し取得せず、途中停止後に残りを処理できることを目標にする | A1で必要項目を確認。既存JSON再利用を優先。既存のmissingFieldsだけでは失敗履歴を表せない点を整理 |
| A3 | 書誌ページの未検証例への対応 | 漫画以外・シリーズなし・項目欠損・年齢確認を必要な順に少数検証する。取得できない例は理由を残し、不明値を推測で埋めない | 必要な例が固定25冊にない場合だけ、追加サンプルの範囲を決める。全件取得はしない |
| A4 | BOOK☆WALKERの所有取得範囲を決める | 通常一覧・アーカイブ・話購入・連携由来等の扱いと、対象範囲の完了判定を決める。公式CSVを利用できるかも比較候補にする | 全件対応の要件整理。CSVは未調査で、採用決定ではない |
| A5 | 継続的な更新方法を決める | 新規購入の追加と既存情報の更新を分け、どの範囲を再取得するか、中断・認証切れ・件数変化時にどう再開するかを決める | A4やストア別取得方式に依存。差分取得可能とは未確認。不在を削除根拠にしない |
| A6 | DB・取得ファイルの運用手順を整える | バックアップ・復元・保存場所・履歴の保持方針をまとめる。ストア別の所有件数、書誌補完状況、最終取得日時を確認する方法を整理する | 今回のバックアップ手順を基に検討。不要ファイルの削除を自動化する決定はしない |

A2〜A6はすべてを一度に実装する計画ではない。A1で優先する利用例を選び、それを満たす最小の作業を選ぶ。全蔵書の一括補完は、対象選択・停止・再開の運用を少数で確認してから別途判断する。

## 保留中の機能

| ID | 作業 | 再開時に確認すること |
|---|---|---|
| B1 | AND・OR条件と表記揺れへの対応 | 全半角の巻数などをクエリーで補う。取得値の厳密な正規化を必須にしない。構文案は[設計検討メモ](03design_notes.md#2-or検索保留) |
| B2 | 読書状態の取得・保存 | 未読・読書中・読了・不明を各ストアでどこまで判定できるか調べる。表示なしを未読とみなさない |
| B3 | シリーズと読書状態を使った検索 | 「続きを買っているが未読」「シリーズで買ったが全く読んでいない」の意味と必要項目を決める。B2とシリーズ・巻順の情報が前提 |
| B4 | 定型検索CLIとSKILL、またはMCP | 実際に使うAI環境と検索手順を確認して接続方法を選ぶ。どちらも現在は低優先度で、専用チャット画面は前提にしない |

## 利用範囲を広げる段階の候補

| ID | 作業 | 着手のきっかけ・範囲 |
|---|---|---|
| C1 | 非プログラマー向けの導入・実行手順 | 自分以外が使う段階で、pnpm・ブラウザー導入、ログイン、取得、取り込み、検索、エラーからの復帰を一通り確認する。配布形式は未決定 |
| C2 | 第3ストアの対応 | 対象ストアを選んでから少数調査する。アダプター登録で再利用できる範囲と、購入日欠損・ページなし取得・利用権等によるモデル変更を切り分ける |
| C3 | ゲーム版への設計の再利用 | 別プロジェクト・別DBとして具体的な対象を決めてから検討する。今の段階で共通SDKや汎用商品DBは作らない |

当面の対象外は、手動メンテナンスを前提とした著者・出版社マスター、厳密な版統合、ローカルLLM／ベクトル検索を必須にする構成、外部プラグインの動的ロード。必要性が実際に生じたときに再検討する。

次の検討としてはA1を推奨する。画面の例外対応を増やす前に、「どの検索を使える状態にしたいか」と「そのために足りないデータ」を一覧にすると、書誌補完・取得範囲の拡張・検索機能のどれを優先すべきか判断できる。
